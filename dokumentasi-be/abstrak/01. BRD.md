# **SAMRS PROJECT BLUEPRINT (MVP)**

**Sistem Manajemen Aset Rumah Sakit - SaaS Multi-Tenant**

## **1. Business Requirement Document (BRD)**

### **A. Objective**

Membangun platform manajemen aset medis dan non-medis yang mendukung banyak rumah sakit (tenants) dalam satu infrastruktur, dengan keamanan data yang terisolasi dan pelacakan aktivitas yang ketat.

### **B. Stakeholders & User Persona**

1. **Dev/SuperAdmin (Global):** Mengelola pendaftaran tenant, monitoring sistem, dan hak akses global.
2. **Tenant Admin (Power User RS):** Mengelola user di dalam RS-nya, mengatur role lokal, dan konfigurasi aset RS.
3. **Technician (User RS):** Mengelola perbaikan, update status aset, dan melihat jadwal maintenance.
4. **Staff/Nurse (User RS):** Melaporkan kerusakan aset dan melihat ketersediaan alat.

### **C. Core Features (Scope MVP)**

* **Multi-Tenancy:** Isolasi data total antar Rumah Sakit.
* **RBAC (Flexible):** Kontrol akses berbasis izin (permissions) yang bisa didelegasikan oleh Tenant Admin.
* **Asset Lifecycle:** Registrasi aset, perpindahan lokasi, hingga penghapusan (Write-off).
* **Audit Trail:** Pencatatan "Siapa, Melakukan Apa, Kapan, dan Bagaimana" untuk setiap mutasi data.

---

## **2. System Architecture**

* **Backend:** Go (Golang) dengan framework **Gin**.
* **Frontend:** React.js (Vite) + Tailwind + Shadcn/UI.
* **Database:** PostgreSQL 15 (Shared Schema strategy).
* **Auth:** JWT (RS256 atau HS256) dengan payload `tenant_id` dan `permissions`.

---

## **3. Database ERD (Entity Relationship Diagram)**

### **A. Core Identity & RBAC**

* **`tenants`**: `id, name, slug, status, created_at`
* **`permissions`**: `id, name, slug, description` (Contoh: `asset:delete`)
* **`roles`**: `id, tenant_id (null if global), name, slug`
* **`role_permissions`**: `role_id, permission_id`
* **`users`**: `id, tenant_id, username, password, role_id, is_active`

### **B. Asset & Maintenance**

* **`locations`**: `id, tenant_id, parent_id, name` (Hierarki Gedung > Ruang)
* **`assets`**: `id, tenant_id, location_id, code, name, brand, status, purchase_date`
* **`audit_trails`**: `id, tenant_id, user_id, action, table_name, record_id, old_value (json), new_value (json), ip_address, created_at`

---

## **4. API Contract Standards**

Semua endpoint akan mengikuti standar ini:

* **Base URL:** `/api/v1`
* **Header:** `Authorization: Bearer <token>`
* **Response Format:**

```json
{
  "success": true,
  "message": "Action description",
  "data": null,
  "meta": { "total": 0, "page": 1 } 
}

```

---

## **5. Audit Trail Logic**

Audit trail akan diimplementasikan sebagai **GORM Middleware/Hook** atau **Gin Middleware**. Setiap kali ada `INSERT`, `UPDATE`, atau `DELETE`, sistem secara otomatis menangkap *state* data dan menyimpannya ke tabel `audit_trails`.
